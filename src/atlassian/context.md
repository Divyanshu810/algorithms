Context
The way we assess candidates, is slightly different compared to other companies
● While most of it is common, and you must be aware of them from your past, we are just going to speak about how it’s split into different pillars for Atlassian
● We will be covering our 5 pillars, and it is important that you qualify in each of these pillars to
get hired during this round.
PART 1 - The generic format of the interview

● For Data Structures interview, we give you leetcode type of problems. You have to make use of the right Data Structures and algorithms to provide the most optimal solution.
● For Code Design, we give you real world problems and you have to do coding for LLD. Topics like OOP principals, Design patterns, Class and Methods will get covered during this round of interview. It's a coding round of interview focused on LLD
● Your calendar will be blocked for 60mins, the first 5mins is for meet and greet, and the last 5mins is for casual question answer session, and you’ll have 45-50mins in between to complete the problem.
● You can use any language of your choice. No restriction on that. You have to set up an IDE and a Testing Framework and whatever you need for coding.
● AI is not permitted, so you would have to disable AI extensions like Copilot if you actively use it.
● You can have a dummy project set up on IDE and build on top of it.
● You’ll have a base problem, which is like Level 1, and as you keep moving forward, they will add more complexity to the base problem.
● There will be 2 levels of extensions, which is basically Level 2 and Level 3.

PART 2 - The way we assess candidates
The 5 pillars are common for both Code Design and Data Structures. You can split and prepare
accordingly.

I. Decision Making :
● This capability gives us an insight into your problem solving thought process and
technical depth and breath that you carry with you.
● So for every given problem we expect you to speak about 3 or 4 different approaches.
● Speak about the pros and cons of each approach, pick the best approach, speak about
the tradeoffs, and use it for implementation.
● We want to know more about the reasoning behind your thoughts.
● You’ll have a base problem and they’ll add more complexity as you keep moving
forward.
● So you have to speak about different approaches for the base problems as well as the
extensions
II. Code Quality :
● Under this, we expect candidates to write production ready code.
● You would have to break down the bigger problem into smaller components and discuss
these in conceptual terms.
● The code written should be modular, and easily reusable in the future.
● It should be maintainable and easily scalable.
● We expect you to write Unit Test cases as a best practice.
● Try to make sure that it covers all the good cases, bad cases, boundary condition or edge
cases.
● It is better if you follow Test Driven Development approach but that’s fine if you are
comfortable writing tests at the end.
● Have a Unit Testing Framework like JUnit if Java / PyTest for Python.
● Dont write tests in Main. It is not Valid. The key idea is to use structured and automated
testing methods instead of ad hoc testing in the main function.
● But please make sure that you test the code or else it might be a red flag.

III. Conceptual thinking :
● We want to see a good understanding of programming fundamentals and concepts
● You will have to cover the below topics
● Time/Space complexity
● Big O Notation - best case, worst case, average case.
● Scalability
● Reliability
● Adaptability of code in different scenarios and environments
● Performance
● Overall Optimisation of code
● You’ll have to drive everything independently and the panel will take the back seat.
IV. Resourcefulness :
● Under this we let people use Google, StackOverflow or documentation of your choice.
● The idea of the whole interview is to understand how you work on a day-to-day basis.
● So we encourage you to use common investigation techniques.
● You can use Debuggers and Print Statements if you need a mini logging and monitoring
set up, just to see if your code is working as intended. But also note, this cannot be
considered as testing. Unit testing has to be separate.
● Just in case if you feel that you got stuck, and if you are not able to unblock yourself and
if you are losing 10-15mins, ask the panel directly to help you out. That should be fine.
Better to keep moving forward as much as possible.

V. Adaptability :
● This is to understand the behavioral side of the candidate. They’ll try to capture a couple
of signals on what kind of thought process you bring to the table.
● They’ll try to understand how easy it is to work with you. So they’ll try to challenge your
decisions and see how you defend yourself.
● Also, they’ll try to understand how you react to uncertainty and unblock yourself. If you
are solving the problem in a particular way, they’ll ask you to stop in between and
suggest a completely different approach, just to see how you unblock yourself.
● They’ll see how you think from a long term perspective while building something. Not
just for the interview’s purpose, but if you have to reuse this code in the future, how
would you think?
● Finally, your solutions have to be customer centric, like putting the customer first.

Part 3 - The mistakes which other candidates have made in the past

1. Solving the problem as soon as it is provided the panels don't appreciate that.
2. They expect you to speak about what you have understood from the problem statement.
3. Then you are expected to speak about the assumptions that you are planning to make and ask good clarifying questions.
4. After that, with the available information, you are supposed to get into the ‘Decision Making’ Pillar. 3-4 different approaches verbally, pros and cons, best approach, and only then you have to start implementing it.
5. A lot of people randomly start building the solution and after 20-30 minutes realise that there could have been a better way to do it.
6. People add unnecessary complexity as they are not sure about what is needed and what is not needed, they end up adding unnecessary components that are not really needed for the problem statement.
7. And unnecessary components take a lot of time and also the code fails.
8. That's why it is better to ask good clarifying questions so that you stay within the scope of the problem.

Not Testing

1. Unit Testing is really important for Atlassian. And it's important to cover all the scenarios like good cases, bad cases, corner cases and whatever possibility is there in testing.
2. Your code should pass through all the scenarios.
3. Some people just write the good cases and make their code pass through it. It's a red
   flag.
4. Printing Tests in main is also a red flag

Naming of Variables

1. You have to pick names which make sense whenever you name a variable or a class or an
   object.
2. You cannot pick random variables like x, y, z.

Not communicating well

1. Some people just come, code, show the output and leave.
2. It becomes very difficult for the panel to understand why you did what you did.
3. It's better to over communicate and tell them every single thing that you are doing.
4. Even if you don't complete the scale ups, they’ll understand your thought process and
   extrapolate and give you a hire if the panel is really kind.

Time Management

1. People spend a lot of time on the base problem itself and they don’t have enough time
   for scale ups.
2. It's understandable that coding becomes slightly rusty as you move into architectural
   roles in your career.
3. You have to practice a little bit of coding daily so that you are able to pick up that speed
   to complete all the 3 Levels to qualify for Atlassian.
